\chapter*{摘要}
\addcontentsline{toc}{chapter}{摘要}

本設計完成一個支援 AES-128、AES-192 與 AES-256 的 AES-GCM authenticated-encryption IP，並以 AXI4-Lite 設定介面、8-bit AXI4-Stream 資料介面與 Arty A7 UART 測試 wrapper 整合。核心以 AES counter mode 產生 keystream，以 GHASH 在 $GF(2^{128})$ 執行驗證；解密 plaintext 在 tag 驗證成功以前不對外釋放，並具備同步 ZEROIZE 與 protocol-abort 清除機制。

本報告把 signoff 分成四個互不代替的邊界：175 MHz full-board implementation 為 \pass，RTL/UVM/NIST dynamic verification 為 \pass，FPGA programming、六模式 smoke 與 47,250 筆 hardware NIST 為 \pass；formal verification 為 \textbf{PARTIAL PASS}，因為目前只完成 19 個 assumption-free combinational proofs，尚未完成 sequential 與 whole-design formal closure。整合 \code{run_all} 為 5 個 suite PASS、1 個 formal suite PARTIAL PASS、0 NOT RUN、0 FAIL。Standalone PartPin 為 \textbf{NO / NOT RUN}；200 MHz 不在本版範圍，也未執行。

最終板級設計在 175 MHz 完成 fresh synthesis、placement、physical optimization 與 routing，並由 immutable routed DCP 進行獨立 v8c strict audit。Routed signoff 為 WNS $+0.029$ ns、TNS $0$、setup failing endpoints $0$、WHS $+0.044$ ns、THS $0$、hold failing endpoints $0$；pulse-width WPWS $+1.607$ ns、TPWS $0$、failing endpoints $0$。17,758 個 routable nets 全部完成 routing，route error、DRC Error/Critical Warning、methodology Error/Critical Warning 與 unsafe CDC category 均為 0。另有 2 個一般 \code{SYNTH-6 Warning}，因此不宣稱 warning-free。

\section{需要正確解讀的限制}

\begin{itemize}
  \item Routed setup margin 為 $+0.029$ ns；若換 Vivado build、constraints、RTL hash 或 implementation directive，必須重跑 signoff。
  \item 0.461 W 為 routed vectorless power estimate，內部 switching activity 信心等級 Medium；它不是電源軌實測值。
  \item 1.05--1.07 Gbit/s 是 RTL/AXI testbench 的 crypto payload throughput。UART 使用 115200 baud，兩者是不同觀測邊界。
  \item Methodology 報告含 2 個 \code{SYNTH-6 Warning}；結果是 Error/Critical-Warning clean，不是 warning-free。
  \item FPGA NIST 47,250 筆已經 exact-bitstream 綁定及兩次 reconciliation 通過；它證明 UART wrapper 的向量正確性，但 39.098 cases/s 仍是 host/UART 交易速率，不是 crypto datapath throughput。
  \item UVM 的 100\% 是維護中 scenario bins 的 functional coverage；目前沒有 code coverage、assertion coverage 或 exhaustive protocol/security coverage。
  \item Formal 結果只涵蓋 17 個 GHASH shift-power 與 2 個 AES S-box combinational assertions；sequential/whole-design formal closure 尚未完成。
  \item PartPin 尚未完成；full-board route 不能取代 standalone PartPin replay。
\end{itemize}

\section{本 AES-GCM 專案如何落實各階段}

\subsection{規格、演算法與微架構}

演算法規格以 AES 與 GCM 的標準運算為基準：AES datapath 執行 SubBytes、ShiftRows、MixColumns、AddRoundKey 與 Key Expansion；GCM 以 counter mode 產生 keystream，並以 $GF(2^{128})$ 的 GHASH 驗證 AAD 與 ciphertext。硬體層不改變演算法結果，而是改變\textbf{運算的排程、平行度、buffering 與資料重用方式}。

為達成 175 MHz 下超過 1 Gbit/s 的核心吞吐率，微架構採三個共享 AES context、兩個 first-block engines、16-entry keystream FIFO、兩筆 sensitive-data queue 與 16-bit digit-serial GHASH。這些結構讓不同 block 的 AES round 能交錯執行，並降低 AES、GHASH、input/output backpressure 彼此等待的比例。安全規格則要求 raw ZEROIZE 能在同一有效 edge 清除敏感狀態、驗證失敗前不得釋出未認證 plaintext，且 queue clear 後 stale head 不得 fire。

\subsection{RTL 與 clock-domain 規則}

核心資料路徑採\textbf{單一 175 MHz 同步 clock domain}；pipeline、FSM、FIFO 與 ZEROIZE priority 都在 clock edge 上更新。非同步方法只用在真正跨 clock/domain 的邊界：例如板級 run request 使用 2-stage \code{ASYNC\_REG} synchronizer，reset deassertion 使用 4-stage synchronous release qualifier。這個分工避免在 AES/GHASH datapath 內加入不可控的非同步 handshake，也讓 STA 能完整分析 register-to-register paths。

RTL 完成後先做 compile/elaboration，檢查未宣告訊號、width、latch 與 multiple-driver；再用 directed tests 重現 reset、key/IV/AAD/data、backpressure、ZEROIZE、authentication failure 與 queue corner cases。UVM 負責 transaction generation、driver、monitor、scoreboard 與 functional coverage，SVA 則對每一個 clock edge 的 protocol/security invariant 做局部檢查。詳細 signal-to-scoreboard 與 property 分工列於第~\ref{sec:end-to-end-verification-flow}~節。

\subsection{Synthesis 與 technology mapping}

Synthesis 的工作是把行為 RTL 轉為 FPGA primitive netlist，並回答三個問題：邏輯是否可合法實現、資源是否放得下、尚未 placement 前的 timing 風險在哪裡。Vivado 會把組合運算映射成 LUT，把狀態映射成 FF，把合適的 memories/FIFOs 映射成 distributed RAM 或 BRAM，並保留 clock/reset/enable control sets。此階段完成不代表時序已通過；synth timing 使用估算互連，實際 net delay 必須等 placement 與 routing 才能確認。

本版板級 routed design 使用 12,411 LUT、9,029 FF、10 個 RAMB18、0 DSP。綜合後的 critical-path family 會依 endpoint primitive、pin type、fanin cone、logic delay 與 net delay 分類；若主要問題是邏輯深度，就調整 pipeline 或 Boolean structure；若主要問題是 control fanout／routing delay，就改善控制訊號 locality、FIFO clear 行為或 physical optimization。

\subsection{Implementation、timing closure 與 signoff}

Implementation 將 synthesized netlist 經過 optimization、placement、physical optimization 與 routing。保留流程的主要指令為：

\begin{lstlisting}[language=tcl,caption={175 MHz implementation 主流程}]
opt_design      -directive ExploreWithRemap
place_design    -directive ExtraNetDelay_high
phys_opt_design -directive AggressiveExplore
route_design    -directive Explore
phys_opt_design -directive AggressiveExplore
\end{lstlisting}

判定不只看「implementation completed」。Setup 必須同時滿足 WNS $\ge 0$、TNS $=0$、setup FEP $=0$；hold 必須滿足 WHS $\ge 0$、THS $=0$、hold FEP $=0$。此外還要確認所有 routable nets 完成 routing、route error 為 0、DRC 與 methodology 無 Error/Critical Warning、unsafe CDC 為 0，且 \code{check\_timing} critical categories 為 0。

最終 routed 結果為 WNS $+0.029$ ns、TNS 0、setup FEP 0、WHS $+0.044$ ns、THS 0、hold FEP 0，17,758/17,758 routable nets fully routed。這表示 175 MHz 的 implementation 與靜態 timing gate 已通過；它仍必須與後續功能與實板結果一起解讀，不能單獨證明 AES-GCM 數學結果正確。

\section{Bitstream、實板驗證與 release evidence}

Signoff routed DCP 通過後才產生 bitstream。燒錄前以 SHA-256 與 manifest 核對 bitstream identity，避免「報告分析 A、板子卻燒 B」。板級驗證再經 UART wrapper 將 NIST RSP case 送入 DUT，checker 逐筆比對 status、ciphertext/plaintext、tag 與預期 authentication failure；目前六模式 smoke 為 6/6，NIST 為 47,250/47,250，fail 0，預期 authentication failure 11,908 筆也全部得到正確分類。

最終 release 必須一起保留 RTL、constraints、SVA/UVM testbench、Tcl flow、synth/placed/routed DCP、timing/DRC/CDC reports、bitstream、board logs 與 hashes。Git commit 負責固定來源版本，artifact manifest 負責把來源、工具版本與輸出 identity 連接起來。如此才能回答「哪一版 RTL、用哪個 Vivado build、哪些 directives、產生哪個 bitstream、在板上跑了哪些 vectors」。

\section{FPGA flow 與 ASIC flow 的界線}

本報告雖以「IC 設計流程」描述數位設計方法，但實際 target 是 Xilinx Artix-7 FPGA。FPGA 的 LUT、FF、BRAM、clock network、placement 與 routing resources 已由晶片廠預先製造，Vivado 完成的是對既有資源的 mapping、place、route 與 bitstream generation；因此本專案沒有 standard-cell library characterization、DFT scan insertion、clock-tree synthesis、power-grid design、IR-drop/EM、LVS、GDSII 或 tape-out。

若未來將核心移植為 ASIC，前端的規格、演算法、RTL、UVM、SVA 與大部分 functional verification 可以沿用；後端則要把 FPGA implementation 替換成 logic synthesis、DFT、floorplan/power planning、standard-cell placement、CTS、routing、parasitic extraction、multi-corner STA、IR-drop/EM、DRC/LVS 與 GDS signoff。這個界線也說明：本報告的「implementation 通過」是\textbf{FPGA implementation signoff}，不是 ASIC tape-out signoff。

\chapter{AES 與 GCM 演算法原理}

\section{AES state、key size 與 round 數}

AES 將 128-bit block 視為 $4\times 4$ byte state。初始先做一次 AddRoundKey；中間 round 依序做 SubBytes、ShiftRows、MixColumns、AddRoundKey；final round 省略 MixColumns。Key size 與 round 數如下：

\midrule

192 bit & 6 & 12 \\
256 bit & 8 & 14 \\
\bottomrule
\end{tabular}
\end{table}

\section{SubBytes：有限體反元素與 affine transform}

SubBytes 是 AES 唯一非線性 round transformation。數學定義為：先在 $GF(2^8)$ 中求 byte 的乘法反元素（0 另行定義），再做 affine transformation；AES 使用不可約多項式
\begin{equation}
  m(x)=x^8+x^4+x^3+x+1.
\end{equation}

目前 RTL 的 \code{sbox.v} 不是在每次運算時計算反元素，而是以完整 256-entry case table 表示 S-box。這是演算法上等價的 lookup-table 方法。實作中：

\begin{itemize}
  \item shared \code{aes_block_engine} 有 16 個 registered S-box，Vivado 將其映射成 8 個 RAMB18；一個 clock 同時處理 state 的 16 bytes。
  \item 兩個 dedicated \code{aes_first_block_engine} 使用 16-way parallel combinational S-box，以 LUT 換取一 round/clock 的短 latency。
  \item key expansion 使用 4 個 registered S-box，映射成另外 2 個 RAMB18。
\end{itemize}

因此板級總計為 10 個 RAMB18。這個選擇保留了 BRAM-based S-box 的規則延遲，也讓 shared engine 的 S-box output 成為顯式 pipeline stage。Reference 資料夾中的 composite-field S-box 文獻說明另一種 area/speed 取捨，但目前 RTL 並未採用 composite-field inversion，不能把該方法誤寫為已實作。

\section{ShiftRows：固定 byte permutation}

ShiftRows 將 state 第 0、1、2、3 列分別循環左移 0、1、2、3 bytes。此操作沒有乘法器或查表，只是 128-bit bus 的固定重新接線。RTL 的 \code{shift\_rows} function 直接重排 bit slices，因此理想上不消耗獨立 arithmetic resources；實際 delay 主要來自 routing 與前後 register/LUT 的組合。

\section{MixColumns：$GF(2^8)$ 固定矩陣乘法}

每一個 4-byte column 乘以下列固定矩陣：
\begin{equation}
\begin{bmatrix}
b'_0\\b'_1\\b'_2\\b'_3
\end{bmatrix}
=
\begin{bmatrix}
02&03&01&01\\
01&02&03&01\\
01&01&02&03\\
03&01&01&02
\end{bmatrix}
\begin{bmatrix}
b_0\\b_1\\b_2\\b_3
\end{bmatrix}_{GF(2^8)}.
\end{equation}

RTL 以 \code{xtime} 實作乘 2：
\begin{equation}
\operatorname{xtime}(a)=(a\ll 1)\oplus
\begin{cases}
\texttt{0x1B}, & a_7=1,\\
0, & a_7=0.
\end{cases}
\end{equation}
乘 3 則為 $\operatorname{xtime}(a)\oplus a$。四個 column 完全平行，只有 shift/XOR/LUT，不使用 DSP。Final AES round 直接選擇 ShiftRows output，繞過 MixColumns。

\section{AddRoundKey：128-bit XOR}

AddRoundKey 為
\begin{equation}
  S_{r+1}=T(S_r)\oplus K_r,
\end{equation}
其中 $T$ 是 SubBytes/ShiftRows/MixColumns 的組合。硬體上是 128 個 parallel XOR。這一層本身不複雜，但 1,920-bit round-key store 的選擇 mux、round-index fanout 與 routing locality 曾是 timing 問題。現在 shared engine 保留四份 4-bit round selector，分別靠近每個 32-bit quarter，避免單一 selector 對 128 個 key bits 的高 fanout。

\section{Key Expansion：RotWord、SubWord、Rcon}

\code{aes_key_context.v} 先擴展並保存最多 15 組 128-bit round keys，共 1,920 bits。每個新 32-bit word 一般為
\begin{equation}
  w_i=w_{i-N_k}\oplus w_{i-1},
\end{equation}
在 $i\bmod N_k=0$ 時，對上一個 word 做 RotWord、SubWord 與 Rcon；AES-256 在 $i\bmod 8=4$ 額外做 SubWord。Rcon 以同一個 $GF(2^8)$ \code{xtime} 更新。

Key expansion 是 iterative FSM，normal word 約 2 clocks，S-box word 約 4 clocks。由 RTL state transition 推得 commit-to-ready latency 為 AES-128 約 100 clocks、AES-192 約 108 clocks、AES-256 約 130 clocks；key ready 後，round keys 由後續所有 records 重用。這能把 key-schedule work 從 steady-state data path 移除，代價是 1,920-bit storage 與前置 key-load latency。

\section{GCM：CTR confidentiality 與 GHASH authentication}

GCM 將 AES counter mode 與 universal hash 結合。先計算
\begin{align}
  H &= E_K(0^{128}),\\
  J_0 &= \begin{cases}
    IV\,\|\,0^{31}\,\|\,1, & |IV|=96,\\
    \operatorname{GHASH}_H(IV), & \text{otherwise},
  \end{cases}\\
  C_i &= P_i\oplus E_K(\operatorname{inc32}(J_0,i)),\\
  T &= \operatorname{MSB}_t\left(\operatorname{GHASH}_H(A,C)\oplus E_K(J_0)\right).
\end{align}

CTR 只需要 AES encryption datapath，解密同樣以 ciphertext XOR keystream 還原 plaintext。GHASH 的 recurrence 為
\begin{equation}
  Y_i=(Y_{i-1}\oplus X_i)\cdot H\quad\text{in }GF(2^{128}),
\end{equation}
field polynomial 為
\begin{equation}
  x^{128}+x^7+x^2+x+1.
\end{equation}

\section{目前 GHASH 的 16-bit digit-serial 架構}

\code{ghash16.v} 每次處理 $X$ 的 16 bits，完成 128-bit multiplication 需要 8 個 digit clocks。Start/load 是獨立 clock，因此外部 initiation interval 為 9 clocks。內部不是串接 16 個 runtime shifts，而是同時建立 $T^0(V)$ 到 $T^{16}(V)$ 的 closed-form linear transforms；依 $X[127:112]$ 選擇 16 個 field terms，再用 balanced XOR tree 做 $16\rightarrow8\rightarrow4\rightarrow2\rightarrow1$ reduction。這將 XOR depth 壓到四層，避免長 XOR chain。

\begin{figure}[H]
\centering
\includegraphics[width=\linewidth]{architecture.png}
\caption{目前 RTL 的 16-bit digit-serial GHASH 資料路徑}
\end{figure}

Reference 文獻中的 Karatsuba-Ofman multiplier、四路 parallel GHASH 與深 pipeline 可達更高吞吐率，但會增加 area、pipeline state 與 verification complexity。目前設計\textbf{沒有使用 Karatsuba}；在 175 MHz 下，GHASH raw block capacity 約為
\begin{equation}
  \frac{128\times175\text{ MHz}}{9}=2.489\text{ Gbit/s},
\end{equation}
已高於 8-bit stream 的理論上限 1.4 Gbit/s，因此現階段不需要以更大 multiplier 換 area。

\section{AES engines：三 context pipeline 加兩個 first-block engines}

主 \code{aes_block_engine} 以 16 個 registered S-box 共用一條 round datapath，保存三份 state contexts。每個 context 的 round recurrence 為三個 pipeline clocks：

\begin{enumerate}
  \item issue context state 與 round index；
  \item registered S-box output，同時選擇 round key；
  \item ShiftRows / MixColumns / AddRoundKey 回寫 context。
\end{enumerate}

三個 contexts 交錯執行，故 single-request latency 約為 $3N_r$ clocks，但 steady-state completion interval 降為 $N_r$ clocks：AES-128/192/256 分別為 10/12/14 clocks。\code{ready} 具有 finish-now look-ahead，可在 context 完成的同一 edge 接受替代 request。

R55 為了解決 175 MHz 下最前面兩個 CTR blocks 的 first-result latency，新增兩個 \path{aes_first_block_engine}，分別專門處理 block index 0 與 1。每個 engine 一 round/clock，latency 為 10/12/14 clocks。後續 blocks 仍由 shared engine 處理；這不是複製三條完整 AES-GCM lanes，而是針對 startup bubble 的局部平行化。

\section{兩筆 sensitive data queue 與 throughput 改善}

第一個 AES keystream result 的 latency 長於 byte stream 完成第一個 128-bit block 的時間。舊架構會在 block boundary 等待 keystream，造成每筆 record 的 bubble。R55 加入兩筆 128-bit sensitive data queue：input blocks 先排隊，等 ordered keystream FIFO head 到達再 XOR、GHASH 或寫 plaintext bank。Queue 支援同 cycle enqueue/dequeue，並在 protocol abort 或 ZEROIZE 同步清除 plaintext/ciphertext-sensitive payload。

這個改動的重點不是提高 clock frequency，而是提高\textbf{每個 clock 的有效工作比例}：把 first-result latency 與 byte admission overlap。搭配兩個 first-block engines，100 筆 1024-bit records 的 cycles 下降到 encrypt 16,820、decrypt 17,039，三種 key sizes 都超過 1 Gbit/s。

\section{FIFO 與 backpressure}

重要 queue 深度如下：descriptor 2、AES request 4、AES metadata 4、AES result 4、keystream 16、GHASH request 4、ciphertext 4、tag packets 2、authenticated plaintext release 2。所有接口使用 valid/ready；AES engine 本身沒有 output ready，故 result FIFO 吸收完成脈衝。Decrypt plaintext 先存於兩個 packet banks，tag comparison 成功後才進 release queue，避免 unauthenticated plaintext leakage。

\section{ZEROIZE 與 security locality}

過往 timing family analysis 顯示，ZEROIZE/control nets 對 FIFO CE/WE、prep registers 與 round-key controls 的高 fanout/locality 是主要 physical risk。最終 RTL 採用 local registered control、one-hot round-key word write enables、分散的 round selector、同步 reset/zeroize priority 與 queue-local clear。Round48/49/53 security regressions、fast-zeroize、data-buffer clearing 與 NIST simulation suites 均通過。

\section{吞吐率公式與測試定義}

吞吐率必須用 payload bits、測量 clocks 與 clock frequency 同時計算：
\begin{equation}
 \text{Throughput} = \frac{N_{payload\ bits}\cdot f_{clk}}{N_{cycles}}.
\end{equation}
Testbench 每個 mode 執行 100 筆 records，每筆 1024-bit data，故加密為
\begin{equation}
 \frac{100\times1024\times175\times10^6}{16820}
 =1.065398\times10^9\text{ bit/s}.
\end{equation}
解密為
\begin{equation}
 \frac{100\times1024\times175\times10^6}{17039}
 =1.051705\times10^9\text{ bit/s}.
\end{equation}

\begin{figure}[H]
\centering
\includegraphics[width=0.88\linewidth]{throughput.png}
\caption{175 MHz 下的六模式 RTL throughput；三種 key size 皆大於 1 Gbit/s}
\end{figure}

Key size 不再改變這個 packet-level measured throughput，是因為最前兩個 blocks 被 dedicated engines 隱藏，後續 shared engine 的 14-clock worst-case II 仍快於 16 clocks/128-bit 的 byte-stream arrival rate。GCM/FIFO/record overhead 使實測值低於 8-bit stream 理論上限 $8\times175=1.4$ Gbit/s。

\section{Latency 與 throughput 的差異}

Latency 是一筆工作從 accept 到 result 的 clocks；throughput 是 steady state 每秒完成多少 payload。Pipeline 可以增加單筆 latency，卻同時降低 initiation interval。例如 shared AES 單筆 nominal latency 可為 30/36/42 clocks，但三 context interleaving 後平均每 10/12/14 clocks 完成一個 block。兩個 first-block engines 則專門縮短 record startup latency。

\section{實板 UART throughput}

板上 NIST wrapper 的 UART 是 115200 baud、8N1。每 8-bit byte 需 10 line bits，因此純 UART payload ceiling 為
\begin{equation}
 115200\times\frac{8}{10}=92.16\text{ kbit/s}.
\end{equation}
每個 frame 還有 command/type 與 16-bit bit-length 共 3 bytes header；例如 128-byte payload 單一 frame 的 wire efficiency 為
\begin{equation}
 \frac{128}{128+3}\times80\%=78.17\%.
\end{equation}
完整 hardware NIST run 共執行 1,208.505 s，平均 39.098 cases/s。這是包含向量長度、frame 數量、host Python、serial turnaround 與 status/data/tag response 的 end-to-end 測試速率，不代表 crypto datapath 的上限。若要在板上直接量測 1 Gbit/s，應改用高速 AXI DMA、Ethernet、PCIe 或純硬體 on-chip counter，不應透過 UART。

\chapter{Timing 問題、同步化選擇與演算法／微架構改善}
\label{chap:timing-sync-algorithm}

本章把前面分散在演算法、RTL 架構、吞吐率與 implementation 章節的重點集中在同一處，直接回答三個問題：遇到 Timing violation 時採用同步還是非同步設計、實際如何把 setup/hold 收斂，以及哪些演算法等價實作與硬體排程改善了吞吐率。核心原則是：\textbf{AES-GCM 的數學定義不變，175 MHz crypto datapath 採同步設計，非同步只存在於受控的板級輸入邊界。}

\section{同步還是非同步：本設計的實際選擇}

AES、GHASH、key expansion、FIFO、AXI4-Lite、AXI4-Stream 與 UART bridge 都由同一個 175 MHz \code{core_clk} 正緣驅動。組合 S-box、XOR 與有限體運算位於同步 register boundaries 之間，因此仍然必須在 5.714 ns clock period 內滿足 STA；它們不是 clockless asynchronous datapath。

  \texttt{rst\_btn}\land\texttt{MMCM LOCKED}

  \;\longrightarrow\;

\end{equation}
Directed reset simulation 證明 1--3 個 sampled clocks 的 pulse 與 alternating chatter 都不會誤解除 reset；連續有效 request 在第 6 個 sampled edge release，無效 request 在第 3 個 sampled edge assertion。Routed CDC audit 只找到預期的 reset request 與 UART RX 兩條 depth-2 safe synchronizers，unsafe CDC category 為 0。Qualifier 最後一級因 distribution fanout 被 implementation physical replication 成 4 個 FF，但它們仍來自同一個 logical reset source，不是四個獨立 reset 或 clock domains。

把內部 AES/GHASH critical path 宣告成 false path，只會隱藏 violation，不會縮短真實 propagation delay；改成 clockless asynchronous handshake 也不會自動消除 LUT depth、fanout 或 routing delay，反而會增加 CDC、metastability、驗證與 BRAM inference 風險。因此本設計以同步 pipeline、register locality 與可檢查的 valid/ready protocol 完成 closure。

\section{實際採用的 Timing 解法}

本設計按下列順序處理 Timing，而不是以一條例外或單一 directive 掩蓋問題：

\begin{enumerate}
  \item \textbf{Memory inference 取代 wide FF arrays：}UART input、data-capture 與 tag-capture 改為 8-bit distributed byte memories，移除大型 indexed mux 與 reset cone。相對 v3，v4 synthesis 減少 10,048 LUT（44.8\%）與 6,434 FF（41.7\%）。
  \item \textbf{建立同步 pipeline boundaries：}shared AES 使用 registered S-box output 與 registered round-key selection，把每個 round 拆成 issue、S-box/key select、ShiftRows/MixColumns/AddRoundKey 三個 pipeline clocks；transform stage 以 valid token 表示資料有效，避免一條高 fanout CE 控制整排 registers。
  \item \textbf{降低 round-key fanout：}1,920-bit round-key store 的 selector 複製為四份，各自服務一個 32-bit quarter，避免單一 4-bit selector 驅動 128 個 key bits。Key expansion 使用 localized one-hot word write enables，每次只寫一個 32-bit word，不讓 FSM decode 直接驅動整個 store。
  \item \textbf{FIFO 與 control locality：}FIFO 使用 registered head、局部 full/count logic 與 queue-local clear；ZEROIZE、protocol-abort 與 sensitive payload scrub 維持同步優先序。非敏感 metadata 在 validity 無效時不必全部 reset，縮小 control cone，但 key/plaintext/ciphertext 等敏感資料仍明確清除。
  \item \textbf{受控 physical replication：}高 fanout reset distribution 可由 Vivado 在 implementation 後複製 physical FF；strict gate 逐份核對來源與 endpoints，確保 replica 仍屬同一 logical control，不引入新 CDC 或不同語意。
  \item \textbf{完整 implementation flow：}依序執行下列 stages：
\begin{lstlisting}[basicstyle=\ttfamily\footnotesize]
opt_design -directive ExploreWithRemap
place_design -directive ExtraNetDelay_high
phys_opt_design -directive AggressiveExplore
route_design -directive Explore
phys_opt_design -directive AggressiveExplore
\end{lstlisting}
  證據只支持整個階段前後的改善，不宣稱某一條 directive 單獨必然修復所有 paths。
  \item \textbf{約束與 hard gates：}只允許真實 asynchronous board I/O exceptions；internal unconstrained endpoints、combinational loops、multiple clocks、unsafe CDC、route errors、DRC Error/Critical Warning 與 methodology Error/Critical Warning 都必須為 0。
\end{enumerate}

\section{最終驗證與可重現性界線}

Final v8c strict audit 的 WNS 為 $+0.029$ ns、TNS 0、setup FEP 0；WHS $+0.044$ ns、THS 0、hold FEP 0；WPWS $+1.607$ ns、TPWS 0、pulse-width FEP 0。17,758 個 routable nets 全部 fully routed，route error 與 DRC violation 為 0，unsafe CDC category 為 0，\code{check_timing} critical categories 全為 0。Dynamic side 另以六模式 throughput、SVA/UVM、security regressions、FPGA smoke 與 47,250 筆 NIST RSP 驗證 cycle、資料、tag、status 與清除行為。

Setup margin 只有 29 ps，屬於窄但為正的 margin；結論只對目前 exact RTL/XDC、Vivado 2021.1 build、implementation directives 與 SHA-matched DCP 成立。更換任何一項都必須重新執行 synthesis、place、phys\_opt、route 與 strict audit。這也是選擇同步設計的主要工程價值：每個 register-to-register path、CDC exception 與 reset topology 都能被明確量測、約束及回歸。

\subsection{三條命令不是同一組 admission checks}

漂亮的概念圖很容易把 KEY\_COMMIT、CMD\_PUSH 與 ZEROIZE 畫成共用一個 checklist；exact RTL 並非如此。三者有不同的安全目的，因此使用三種不同規則：

\begin{enumerate}
  \item \textbf{CMD\_PUSH：}建立一筆 record descriptor。接受條件為 key 已 ready、descriptor FIFO 未滿、Core 不在 ZEROIZE、IV length 不為 0、tag length 符合本 build policy。它刻意\textbf{不要求}目前 record 或 public output 完全 idle，只要 descriptor FIFO 有空間，就能讓下一筆 descriptor 預先排隊。
  \item \textbf{KEY\_COMMIT：}把 256-bit staging key 與外部 \code{key_mode} 交給 key expansion。接受條件為 \code{key_mode} 只可為 0/1/2（AES-128/192/256）、key engine 不 busy、Core key lifecycle quiescent、Data skid 與 Tag FIFO 沒有 boundary residue、Core 不在 ZEROIZE。它不使用 IV/tag length 或 CMD\_FULL 作為條件。
  \item \textbf{ZEROIZE：}standalone、格式合法的 ZEROIZE write 不依賴上述 lifecycle 狀態而被 state-reject；它是 emergency flush，不是「等輸出 drain 完再清除」。但若同一 CONTROL write 同時設了其他 command bit，仍因 command 不具原子唯一性而回 \code{SLVERR}。
\end{enumerate}

Default production build只接受 128-bit tag；當 \code{ALLOW_NIST_TAG_LENGTHS=1} 時，另外接受 32、64、96、104、112 與 120 bits。CFG write 本身只保存值並回 OKAY，真正的 tag-policy validation 延後到 CMD\_PUSH；這使設定階段與 descriptor admission 的錯誤責任清楚分離。任何被拒絕的 CMD\_PUSH/KEY\_COMMIT 都只回 \code{SLVERR}、不產生 pulse、也不改變 Core；目前沒有 sticky error register，因此 software 必須檢查每一筆 B response。

\subsection{Input plane：2-entry registered-head queue 與 frame credits}

公開 input 不是直接接到 Core，而先進入一個 2-entry、9-bit FIFO；每一 entry 保存 1-bit \code{TLAST} 與 8-bit \code{TDATA[7:0]}。這個 queue 的設計目的有兩個：第一，用 registered head 暫存 byte；第二，以 registered \code{s_axis_tready_r} 切斷複雜的 Core byte-acceptance logic 到 public READY 的組合路徑。

\code{input_frame_credits} 不是 FIFO occupancy，也不是整筆 transaction 的 lifetime counter。它精確表示「已成功 CMD\_PUSH、但 public input TLAST 尚未 handshake 的 frame 數量」：

\begin{itemize}
  \item 成功的 CMD\_PUSH 增加一個 credit；
  \item public \code{TVALID} \&\& \code{TREADY} \&\& \code{TLAST} 減少一個 credit；
  \item 同一 edge 同時 CMD\_PUSH 與 TLAST handshake 時淨變化為 0；
  \item 沒有 credit 時 public READY 一定為 0，因此 software 不可能在 descriptor 被接受以前塞入資料；
  \item early TLAST 會先在 public boundary 歸還 credit，Core 之後再回報 framing abort；late TLAST 則保留 credit，直到 drain 過程真的收到後續 TLAST。
\end{itemize}

READY 使用 predictive occupancy：每個 edge 根據本拍 push/pop 後的 queue count 與下一拍 credit 狀態，決定下一 cycle 是否仍可接資料。Reset 後 READY 為 0；CMD\_PUSH 被取樣後，credit 與 registered READY 在 edge 更新，最快下一個 edge 才可能接收第一個 byte。當 queue 同時 pop 與 push 時可維持每 clock 一 byte；若無 pop 且本拍接收使預測 count 變成 2，下一 cycle READY 會先行拉低，避免 overflow。

\subsection{ZEROIZE：emergency flush，而不是 graceful drain}

ZEROIZE pulse 是 AXI register bank 完成 buffered CONTROL write dispatch 後產生的 synchronous one-cycle event。Pulse 為 1 的 cycle，Wrapper 立即將 public input READY 與所有 public output VALID gate 為 0；在取樣 pulse 的 active edge，input FIFO、Data skid、Tag FIFO、input credits 與 boundary trackers 都被 synchronous clear/reset，key staging 清為 0，同一 pulse 直接送進 Core 啟動 sensitive-state invalidation 與 plaintext-bank scrub。

這個定義有四個必須明說的界線：

\begin{enumerate}
  \item 已經完成 public handshake 的 byte 無法被撤回；ZEROIZE 只能阻止尚未 handshake 的公開資料。
  \item 這是 flush semantics。被 stall 的 VALID 可以被撤銷，partial Data/Tag frame 可以被截斷，ZEROIZE 不為它補 synthetic TLAST。
  \item generic FIFO 的 clear 會清 pointers、count、registered head 與 validity，使 stale entry 不再可觀察；它不是對每個 backing \code{mem[]} word 逐位物理抹除。若產品威脅模型要求 memory remanence scrub，必須另加 explicit overwrite 或使用具有 erase guarantee 的 storage policy。
  \item Core 只對「Result 尚未退休」的 unfinished descriptors保留對應的 \code{ZEROIZE_ABORT} 債務。若 \code{DEC_AUTH_OK} 已 handshake、但 authenticated plaintext 尚在 release path，ZEROIZE 可丟棄剩餘 plaintext而不再產生第二個 abort result；這和 emergency flush 定義一致，但不能宣稱每一個尚未輸完的 byte 都會得到替代 Result。
\end{enumerate}

\newpage
目前 Wrapper 連接但不採用 \code{core_zeroize_defer}，因此 policy 明確偏向立即 flush。若未來產品規格改成「先保存／drain 已認證輸出，再 scrub」，就不能只修改文件；必須把 release-producer、allocated plaintext bank、boundary buffer 與 repeated ZEROIZE 都納入 defer contract，再以 SVA 和 directed fault injection 重新驗證。

\subsection{Protocol abort 與 ZEROIZE 的差異}

TLAST protocol error 是單一 record 的協定錯誤，不應破壞已排隊的其他 descriptor。Early TLAST 進入 abort wait；late TLAST 進入 drain 並丟棄 byte，直到收到後續 accepted TLAST。若 encrypt 已有 prefix 跨越 Core boundary，Core 會送 synthetic zero/TLAST terminator，再送 abort Result。這條路徑不會像 ZEROIZE 一樣清掉 top input queue、Data skid、Tag FIFO、descriptor FIFO 與舊的完成結果。

Core 內部在 abort flush 時可以更換尚未被 Core-output handshake 接受的 stalled beat；public boundary 的 Data skid 會保護已被 Wrapper 接受的公開 beat，使外部一般 AXI stability 仍成立。因此若未來有人直接繞過 \code{aes_gcm_axi_top} 使用 \code{aes_gcm_stream_core}，就必須自己加等價 output buffering，不能假設 Core raw interface 已具有相同 public guarantee。

\subsection{設計取捨、可驗證性與報告結論}

此 Wrapper 選擇的不是「每一條 channel 都加很深 FIFO」，而是針對問題配置最小結構：input 需要 registered READY 與 command credit，因此用 2-entry queue；Data 需要一拍 elasticity 與 payload hold，因此用 one-entry skid；Tag 需要在 Data 尚未結束時提前吸收 byte，因此用 2-entry FIFO；Result 只需要防超車，因此使用 frame gate而不加 FIFO。代價是 ordering logic與 mode semantics較複雜，但可避免不必要的 area/latency，並讓每個 correctness property 有清楚的 checker boundary。

報告這一頁時可用一句話收斂：

\begin{quote}
\textbf{我把 AXI Wrapper 設計成同步的 protocol/security boundary：control plane 將 software write 原子化為不同 admission 規則的命令事件；input queue 與 output buffers 管理 byte-level backpressure；outermost frame trackers保證公開順序；ZEROIZE則採立即 flush並觸發 Core scrub。它的目的不是做 AES-GCM運算，而是讓同一個 Core 能以可整合、可 timing、可驗證的方式進入真正系統。}
\end{quote}

主要 code anchors 為 \path{aes_gcm_axi_top.v:94--100}（admission）、\path{aes_gcm_axi_top.v:139--211}（input queue／credits／registered READY）、\path{aes_gcm_axi_top.v:280--378}（public frame ownership／outputs）與 \path{stream_axi/axi_lite_regs.v:127--290}（CONTROL dispatch／register write semantics）。Vivado 原生 schematic 可證明 \code{u_registers}、\code{u_input_queue}、\code{u_core}、\code{u_data_output_register} 與 \code{u_tag_output_register} 的 hierarchy/connectivity；UVM/SVA/NIST 則分別證明 transaction result、cycle-level invariant 與標準向量 correctness，三者不可互相取代。

\subsection{SVA、UVM、Vivado與實板 checker 的分工}

\begin{lstlisting}[language=Verilog]
assert property (disable iff (!rst_n || clear)
    (valid && !ready) |=>
    (valid && $stable(payload)));

assert property (disable iff (!rst_n)
    zeroize |=>
    (!ready && !busy &&
     round_count == 0 && round_keys == 0));
\end{lstlisting}

\section{Verification plan、oracle 與 comparison chain}

驗證不以「模擬跑完」作為 PASS，而是先把需求轉成可觀測 stimulus、獨立 expected value、checker 與可保存證據。資料流如下：

\begin{center}
\small
\fbox{AXI / UART stimulus}
$\rightarrow$ \fbox{DUT accepted handshakes}
$\rightarrow$ \fbox{passive record reconstruction}
\\[2mm]
$\rightarrow$ \fbox{independent reference / RSP oracle}
$\rightarrow$ \fbox{scoreboard / hard gate}
$\rightarrow$ \fbox{CSV、JSON、JSONL、RPT、SHA-256}
\end{center}

UVM checker 不直接使用 sequence 或 driver 內的 expected transaction。\path{passive_record_reconstruction_monitor} 從實際 AXI-Lite AW/W handshakes、AXI-Stream input handshakes，以及 data/tag/result output handshakes重建完整 record，再送進 scoreboard。Driver 與 checker 不共用同一 transaction object，可降低 stimulus 與 checker 同源錯誤；orphan output、缺少 result 或 timeout 都是 checker failure。

Golden model 位於 \path{verification/uvm/aesgcm_reference_model_pkg.sv}。AES S-box 由 $GF(2^8)$ 反元素與 affine transform 計算，不重用 DUT lookup table；GHASH 採 NIST SP 800-38D 的 128-step bit-serial multiplication，不重用 DUT 16-bit digit-serial datapath。Model 先以 FIPS-197 AES 與 SP 800-38D GCM 範例自我核對，再作為 UVM transaction-level oracle。

Scoreboard 對 encryption 比對完整 output payload、authentication tag 與唯一 result byte，且 success result 必須為 \code{0x00}；對 authentication-success decrypt 比對完整 plaintext，並驗證 success predicate。對 authentication-failure decrypt，UVM 要求不得釋放 plaintext，並檢查 \code{(result == 0x01) == auth_ok}；目前\textbf{沒有}強制失敗碼必須精確等於 \code{0xFF}。精確 \code{0xFF} failure status、空 data 與空 tag 是 FPGA NIST host runner 的另一個嚴格 checker boundary，不可誤稱由 UVM 完成。

FPGA NIST 不使用 UVM model 當 oracle，而直接使用六份 NIST \code{.rsp} 的 expected status、ciphertext/plaintext 與 tag。Encrypt 必須回傳 \code{0x00}、exact ciphertext 與 exact tag；successful decrypt 必須回傳 \code{0x01} 與 exact plaintext；RSP \code{FAIL} 必須回傳 \code{0xFF}，而且 data/tag 都為空。JSONL reconciliation 不重新計算 AES-GCM；它獨立檢查 47,250 行、indices 0--47,249 連續唯一、六個來源各 7,875 筆、分類數與 mismatch counters，避免只相信 aggregate PASS marker。

\section{SVA：cycle-by-cycle temporal checker}

本設計使用 SystemVerilog Assertions（SVA）檢查「某個 clock edge 發生事件後，當下或下一個 edge 必須成立的局部時序規則」。SVA checker 放在 \path{verification/sva/}，由 \path{bind_all.sv} 依 module type 綁入 \code{ghash16}、\code{aes_key_context}、\code{aes_gcm_stream_core} 與 \code{aes_gcm_axi_top}；production RTL 不需插入 checker，也不把 SVA 納入 synthesis/bitstream。checker 可以觀察 DUT 內部 state、queue count、round keys 與 output handshake，因此比只看 transaction 最終結果更早指出違反規則的 cycle 與 property 名稱。

Property 以正緣 clock 取樣。\code{|->} 用來檢查同一取樣 edge 的 implication，\code{|=>} 檢查下一個 edge；\code{\$past(...)} 比對前一拍資料，\code{\$stable(...)} 檢查 backpressure 或 blocked queue 期間不得改變。依 property 使用 \code{disable iff (!rst\_n)}，並在適用處加入 ZEROIZE 或 logical clear，使 reset/scrub/flush 的無效觀察窗不造成誤報；相對地，ZEROIZE 本身需要產生的 key/queue 清除效果由獨立 assertions 明確檢查。

GHASH checker 沒有呼叫 DUT 的直接 $T^{POWER}$ 邏輯。它以 NIST shift/reduce 的 one-bit reference 重算 $T^{16}$、16-bit digit product 與完整 $GF(2^{128})$ multiplication recurrence，再逐拍比對 digit-serial DUT；這可避免 checker 與 DUT 使用完全相同實作而一起犯錯。AXI 與 tag assertions 則針對 ready/valid protocol、TLAST 與 backpressure 保持性做 cycle-accurate 檢查。

執行時，\path{verification/scripts/common.sh} 先列出 production RTL 與六個 SVA/bind sources；\path{run_smoke.sh} 依序呼叫 \code{xvlog -sv}、\code{xelab}、\code{xsim}，跑 GHASH standalone 與 AXI integration。Runner 只有在 \code{GHASH16_PASS tests=66}、\code{AXI_SMOKE_PASS cycles=7676} 都出現，且 log 完全沒有 \code{Assertion failed} 時才回傳 PASS。本輪 retained integrated replay 的 smoke 為 0 assertion failures。\path{run_nist.sh} 也編入同一組 SVA，完整 simulation 為 47,250/47,250、fail 0、17,740,527 cycles，且同樣以任何 assertion failure 作 hard fail。

SVA、UVM 與 formal 的責任不同：UVM 由 transactions、independent golden model 與 scoreboard 檢查 end-to-end data/tag/status；SVA 在這些 dynamic simulation traces 上逐拍檢查局部 control/protocol invariants；Yosys SAT 的 19 個 combinational assertions 是另一組 formal harness，並不是這 37 條 SVA 的 exhaustive proof。目前 SVA 來源內沒有 \code{cover property} 或 \code{assume property}，也未收集 property activation、vacuity 或 assertion coverage，所以只能宣稱「retained tests 中 0 assertion failures」，不能宣稱 37/37 都被觸發或 100\% assertion coverage。它也不是 post-route、實板、sequential whole-design、liveness、CDC、timing、power 或 side-channel formal proof。

證據 provenance 另有一個已知缺口：retained \path{verification/results/sva/sva_summary.md} 仍記錄舊 RTL SHA，因此 current 判定採用 promotion manifest 綁定的 integrated \path{run_all.log} 與 retained smoke/NIST logs；現有 SVA runner 尚未像 UVM runner 一樣保存每個 compile input 的 SHA-256。後續應補上 compile-input manifest 與 activation/vacuity coverage，再提升成 exact-source SVA attestation。

\chapter{結論與後續工作}

本版已完成可燒錄的 Arty A7-100T AES-GCM 實作，175 MHz v8c strict static audit 的 setup、hold、pulse-width、route、DRC、methodology E/CW、CDC/reset schema 與 \code{check\_timing} hard gates 全部通過。Hardware-tested v8a bitstream 的 configuration \code{.bin} 與 v8c strict-audit \code{.bin} 完全相同；六模式 smoke 為 6/0，full hardware NIST 為 47,250/47,250、fail 0，且第二次獨立 reconciliation 通過。核心透過兩個 first-block engines、三 context shared AES pipeline、16-entry keystream FIFO、兩筆 sensitive data queue 與 16-bit digit-serial GHASH，在單一 8-bit stream 下達到 1.065398 Gbit/s encryption 與 1.051705 Gbit/s decryption。

驗證結論必須保持分層：static implementation、dynamic simulation/UVM/NIST 與實板驗證都是 PASS；integrated overall 是 \textbf{PARTIAL PASS}，唯一原因是 formal 僅涵蓋 19 個 combinational assertions，並非任何 suite failure 或 NOT RUN。UVM、FPGA NIST 與 routed audit 使用不同 oracle/checker，互相補強但不互相取代。

Standalone OOC PartPin 狀態仍為 \textbf{NO / NOT RUN}：目前沒有 approved、identity-matched production \code{HD.PARTPIN\_LOCS} map 與 parent timing model。此限制與已通過的 full-board route 是不同 signoff boundary。

下一步建議依風險排序：

\begin{enumerate}
  \item 封存 v8c strict-audit 與 v8a board evidence 的 manifest、SHA-256 與 reconciliation 規則；未來重跑必須先核對 routed DCP 與 configuration image identity。
  \item 以代表性 SAIF/VCD 重跑 power，或量測 FPGA 電源 rails，替換 Medium-confidence vectorless 數字。
  \item 擴充 sequential formal adapter/solver，覆蓋 GHASH control、FIFO/ZEROIZE temporal behavior 與 top-level liveness；不把 19 個 combinational assertions 誤當 full closure。
  \item 若交付範圍需要 PartPin，先取得 approved identity-matched production map 與 parent timing model，再執行 strict replay。
  \item 若要證明板上 crypto datapath 的 1 Gbit/s，而不只是 simulation，加入 on-chip cycle counter + BRAM traffic generator，或改用 Ethernet/PCIe/高速 AXI DMA。
  \item 若要正式交付 Vivado Block Design，將 \code{aes_gcm_axi_top} 另行 package 成 IP-XACT，並建立 CDC、register-map 與 driver 文件。
\end{enumerate}
